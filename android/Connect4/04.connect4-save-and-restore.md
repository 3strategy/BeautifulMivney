בסוף הפרק הלוח והתוצאה ישרדו סיבוב, מעבר לרקע ופתיחה מחדש. נבדיל בין שמירת אובייקט בזמן סיבוב לבין שמירת מידע לאחר סיום התהליך.

`ViewModel` שומר את `GameSession` כאשר Android יוצר Activity חדש בסיבוב. הוא אינו דיסק ואינו שורד סיום תהליך. `SharedPreferences` שומרת את רצף העמודות; ממנו בונים מחדש את המשחק. לא שומרים תמונה של המסך או 42 ערכים נפרדים.

## השינויים לפי סדר העבודה

### GameSession.java

<div markdown="1" class="english">

**app > kotlin+java > com.example.connect4 > GameSession.java**

</div>

צרו את המחלקה בחבילת האפליקציה. אין בה הפניה ל־Activity או ל־View: אלה מוחלפים בסיבוב. הדגל `restored` מונע מה־Activity החדש לדרוס משחק שכבר נמצא ב־ViewModel.

```java
package com.example.connect4;

import androidx.lifecycle.ViewModel;
import com.example.connect4.core.GameEngine;

/** Retains the game across Activity recreation, without keeping a View or Activity. */
public final class GameSession extends ViewModel {
    public GameEngine engine = new GameEngine();
    public boolean restored;
}
```

### MainActivity.java

<div markdown="1" class="english">

**app > kotlin+java > com.example.connect4 > MainActivity.java**

</div>

מקבלים את אותה Session דרך `ViewModelProvider`. ביצירה הראשונה בלבד משחזרים היסטוריה. כל תו הופך לעמודה ועובר דרך `apply`, בדיוק כמו נגיעה. אם המידע מכיל מהלך אסור, עוצרים ושומרים את הקידומת החוקית; לא מכניסים נתונים ישירות למערך.

שומרים אחרי מהלך ואחרי New game, וגם ב־`onStop`. כך אין תלות ב־`onDestroy`, שלא מובטח שייקרא לפני סיום תהליך. `SharedPreferences.Editor.apply()` מעדכנת בזיכרון ושומרת ברקע; זו מתודה אחרת מ־`GameEngine.apply()` למרות השם הזהה.

## מריצים ובודקים

1. שחקו כמה מהלכים וסובבו: אותו לוח ואותו תור מופיעים.
2. עברו למסך הבית וחזרו: אין שינוי.
3. סגרו את האפליקציה ופתחו מחדש: הרצף נשמר. בדקו גם משחק שכבר הסתיים.
4. לחצו New game, צאו ופתחו: מופיע לוח ריק.

בדיקת המורה מזריקה היסטוריה עם מהלך אחרי ניצחון ומוודאת ששוחזרה רק הקידומת החוקית. בדיקת יצירת Activity חדש אינה לבדה הוכחה להריגת תהליך; במכשיר בודקים גם סגירה ופתיחה מחדש.
